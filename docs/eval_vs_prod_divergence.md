## 为什么会积起来

生产与评测**共用同一个术语库文件**（`.env` 的 `TERMBASE_PATH=termbase/auto_regulation_terms_v1.csv`），
但服务器那份按部署冻结、本地那份随评测演进，两边就此分叉。

- 2026-07-28 起 `api/deploy/selfcheck.py` 每 10 分钟断言生产术语库 md5 不变
  （与 `reasoning_tokens == 0` 并列的外部漂移哨兵）。它**防的是"被无意改动"**，
  不解决"该上而未上"——那要靠这张清单。
- V2 的两臂都用 `/data/SERVICE_USER/translation-eval/tb/` 下的副本，
  `translate_local_npu.py --termbase` 指定，**不触碰生产那份**。

### 代码副本漂移（2026-07-29 查实，同型失败第四次）

术语库会分叉，**代码副本一样会**，而且没有 md5 哨兵盯着。服务器上有两份：

| 路径 | `scripts/common/termbase.py` md5 | 状态 |
|---|---|---|
| `PROJECT_ROOT`（下称 REPO） | `7ba3478a` | **冻结**，无 S3a span 抑制 |
| `/data/SERVICE_USER/translation-eval/localsrc` | `38cc5ef6` | 与本地当前版一致 |

两版 `match_terms` 在 689 条源文上的差：**34.8% 的源文匹配列表不同，硬术语数 1392 vs 1147（+21.4%）**。

- **生成侧**：`translate_local_npu.py`（臂A）、`y3_gen.py`、`c1_gen.py` **三者都解析到 REPO**
  （`translate_local_npu.py` 的候选路径里 `20260727/` 无 `scripts/`，直接回落到 REPO）。
  → 三臂注入的术语列表口径**一致**，臂A/Y3/C1 之间的对比干净；
  → 且该口径**恰好与生产一致**（生产也是未修复版，即第 2 项）。这是巧合，不是设计。
- **打分/TCR 侧**：已发布的 96.51% = **1107/1147**，用的是**修复版**、在**全集 689** 上算。
- **因此**：`/data/SERVICE_USER/translation-eval/c1_analyze.py` 引用 REPO 且在 627 上算 TCR，
  会得到 ≈79.5% 并把所有臂判为"否决"，**且不报错**。该脚本已作废，
  分析改为本地 `scripts/analysis/c1_analyze.py`，三条护栏（术语库 md5 / 硬术语数 1147 /
  臂A TCR 1107·1147 与 506·545）任一不符即抛错，不出数。

**教训**：凡是要出对外数字的脚本，不接受"能跑通"作为正确性证据，
必须先复现一个已知的已发布数才允许往下算。

### 依赖版本漂移（2026-07-29 查实，同型失败第五次）

术语库会分叉、代码副本会分叉（第四次），**第三方库版本一样会**，而且同样没有任何哨兵盯着。

本地 `.venv` 在本次会话之前**从未装过 `pdfplumber`**（小语种 Z0 盘点第一次要跑
`--mode from_raw` 时 `ModuleNotFoundError`）。临时 `pip install` 抓到当前最新版
（`0.11.10`/`pdfminer.six 20260107`）跑 en-zh/ru-zh，复现不出已发布的 **689/103**：
本地重跑给出 en 1019 条（exact 907）、ru 72 条（exact 67）。

排查过程：
- 代码没变（`git log 3052324..HEAD -- scripts/evaluation/prepare_da_pairs.py` 为空）；
- 数据没变（`data/raw/` PDF 被 git 强制跟踪，`git diff HEAD` 干净）；
- 找到最有希望的候选版本：服务器三个独立 conda 环境（`ascend`/`clip`/`gac_qwen_zh`）
  的 `pdfplumber` 一致为 `0.11.9`（安装于 2026-06-10，早于全部修复提交）。装上重跑，
  **与 0.11.10 逐字节相同**（`aligned_da_samples.jsonl` md5 一致）——版本假设被推翻，
  真正差异源未查清（怀疑是当初产出 689/103 那次运行的机器/环境，但已超出"比较两个
  pdfplumber 版本"能验证的范围）。

**处理**：按"找不到/复现不出"的既定规则——**锁定 `pdfplumber==0.11.10`
/ `pdfminer.six==20260107`，连同 `requests==2.34.2`、`unbabel-comet==2.2.7`
一并写死进 `scripts/requirements.txt`**（此前一个都没锁）。**en 689 条以落盘文件为准，
永不重抽；ru 的历史 103 作废，以锁定版本重新产出的 67 为准（低于合同 100 条门槛，
Z1 需要补足）。** 锁定版本对全 7 语向跑出的结果存为「基线快照」
（`outputs/analysis/z0_minor_lang_20260729/baseline_snapshot_v1/`），
此后抽取器改动一律对照这份快照做漂移检查，不再对照可能已经漂移的历史数字。

**教训**：环境从未被声明为交付物的一部分，这是第三次"某样东西分叉了但没人盯"
（术语库文件、代码副本、现在是依赖版本）——同一个类型的失败，同一个没做的动作：
锁版本 + 哨兵。`requirements.txt` 缺失多年没暴露，是因为此前从没人在一台"干净"的
机器上重跑过这条流水线。

### match_terms 词边界只认拉丁字符（2026-07-29 查实，同型失败第六次，**影响生产**）

Z1(ru) 首次跑出 TCR 74.07%（否决）。逐条排查发现 `scripts/common/termbase.py`
的 `_term_spans()` 词边界正则写死 `[A-Za-z0-9]`，不认西里尔（也不认阿拉伯语/
泰文）——GOST 术语库里"气候版本"缩写别名 "ХЛ" 在完全无关的俄语单词内部
（"**охла**ждающей"＝冷却）被误判命中，单这一条贡献了 12/14 处 TCR 失败。

**这次不是纯 eval 侧问题**：`_term_spans` 是 `match_terms()` 的核心函数，
**生产 `api/backends/base.py` 的 `build_translation_messages()` 直接调用它**
做术语召回与 prompt 路由——任何非拉丁语向（ru/th/ar，以及 de/fr 里含重音字母的
短别名）只要术语库里存在短别名，生产环境都可能撞上同一个坑，不只是评测算错分，
是**生产可能给错误的术语召回结果、进而影响实际翻译的术语提示**。

修法：词边界判据由 `[A-Za-z0-9]` 改成 Python 的 Unicode 感知 `\w`。
**漂移检查**：EN 的 TCR（1107/1147=96.51%、506/545=92.84%）修复前后逐字节不变，
已验证，不影响任何已发布的 EN/C1/Y3 数字。ru 修复后 TCR 从 74.07% 升到
90.48%（仍未过 95%，但确认是真实缺口，不再是 bug 噪声）。

**这是本轮第四次同型"Latin-only 字符集假设"bug**（前三次：`SECTION_PATTERNS[2]`
缺西里尔附录字母、`good_char_ratio` 缺阿拉伯展示形字符、`_SENT_EN` 缺西里尔大写
判断——全部记在 `outputs/analysis/z0_minor_lang_20260729/README.md`）。
**教训**：任何写死 `[A-Za-z0-9]`/`[A-Z]` 的正则，只要可能处理非拉丁语向文本，
都要先假定它是错的，逐个语向验证，不能等某个语向"刚好撞上"才发现。

### "修一个语向、炸另一个语向"的两次教训（2026-07-29，Z2-de / Z3-ar）

**第一次（标题引用去重）**：de 的 § 条款目录页重复问题，第一版实现（同 key 多次
出现时，剔除明显更短的那个）跑漂移检查发现 en 少 15 条、ru 少一批、fr 也变了，
**当场撤回**。逐条核查后发现消失的全部是 `scoped_ambiguous`/`order_based`
（本来就 `use_for_da=False`，不进正式语料），没有一条 `exact_section_scoped`
被动，fr 甚至净增 1 条——**是此前的漂移检查口径定得过严**（守护了"整个
`aligned_da_samples.jsonl` 不变"而不是真正要紧的"`exact_section_scoped`
子集不变"），确认安全后重新加回，**副作用是正面的**：同一个问题在 en/R100
（"3.2. Component based test"标题 vs "3.2. Test procedure..."正文共享条款号）
和 ru/GOST 里也存在，这次一并修了。

**第二次（阿拉伯语展示形字符归一化）**：第一版用 `unicodedata.normalize("NFKC", text)`
对整个字符串生效，跑漂移检查发现 **541/689 条 EN 内容不一致**——NFKC 会把
英语文本里当撇号用的重音符号 U+00B4 分解成"空格+组合重音符号"，这次是**真实
的、必须撤回的漂移**（不是护栏过严的误报）。改成只对阿拉伯语展示形式区
（两个 Unicode 区间）建窄范围字符映射表，`str.translate()` 只转换这批字符，
重新验证零漂移。

**两次教训合起来的规矩**：
1. 任何触碰共享函数（`align_segments`/`clean_text`/`is_noise_line`）的改动，
   跑漂移检查跑出差异**不能直接判定"危险，撤回"**，要先查清楚差异具体是什么
   （哪个字段、哪个置信度类目、是否真的影响 `exact_section_scoped`/`use_for_da=True`
   的数据），再决定撤回还是保留——过严的护栏和过松的护栏一样会导致错误决策。
2. 但查清楚之前，**先撤回再说**，不能带着未验证的改动继续往下游跑——两次都是
   "撤回 → 逐条核查 → 有依据地决定"，不是"跳过验证直接判断"。
3. 任何"归一化/转换"类改动（NFKC、大小写折叠、全角半角转换……）默认视为
   **全局副作用未知**，只在明确需要的窄范围（字符集、语言）生效，不要图省事
   对整个字符串生效——这条本来就该在第一次实现时想到，NFKC 对标点/重音符号
   的兼容分解是 Unicode 标准里写明的已知行为，不是冷门陷阱。

### 服务器热修未回灌仓库（2026-08-02 查实，分叉事件第 4 起 / 同型失败第七次）

前三起分叉都是"**仓库改了、服务器没上**"（术语库版本、span 修复、target_alias）。
这一起方向**正好相反**：**服务器改了、仓库没收**。

2026-07-30 在 220 现役副本 `/data/SERVICE_USER/translation-api/regression.py` 上热修了 C 段：
上限由写死的 `7500` 改成读 `.env` 的 `MAX_TEXT_CHARS` 并取 95%。原因是 `MAX_TEXT_CHARS`
已从 8000 降到 6000，写死 7500 会直接撞 422 超限，把"截断保护"这一项**测成参数校验**。

该热修**从未回灌** `api/examples/regression.py`。直到 2026-08-02 部署 125 时，
在新机上跑仓库版才发现 C 段输出 `code=422 超过上限 6000` —— 与 220 上跑出来的完全不同。

两条独立的教训：

1. **分叉是双向的。** 只防"仓库→服务器"漏部署是不够的，"服务器→仓库"漏回灌同样发生，
   且更隐蔽：服务器上那份能跑通、结果还更对，没有任何人有动机去回灌。
2. **两台机并存把分叉面翻倍。** 220 与 125 各有一份代码、一份 `.env`、一份 systemd 单元。
   靠人肉比对必然漏——前六次同型失败已经证明人肉比对不可靠。

**修法（2026-08-02，与本次 220 切 4188 同批上线）：**

- 热修行为回灌仓库版 `api/examples/regression.py`，并把 `BASE`/`PROJECT`/`REF`
  改成环境变量可配，两台机**共用同一份脚本**，不再各存一份。
- 新增 `api/deploy/make_manifest.py` 生成 `api/deploy/DEPLOY_SHA256SUMS`，
  覆盖 `api/` 与 `scripts/common/` 下全部生产 Python；自检每轮校验，不符即
  `manifest_mismatch` 落进 `failed`。**这是第一个能自动发现代码分叉的哨兵**——
  此前只有术语库 md5 一项，而第四、五、六次失败都不在术语库上。
- 清单必须与代码同一个 commit：只改代码不重生成清单，自检立刻报，这是设计意图。

**仍未覆盖的**：`.env`（机器专属、含密钥，不进清单）、systemd 单元、venv 依赖版本。
这三项目前仍靠差异清单人工维护，是下一个该上哨兵的地方。
